# macOS Electron API Coverage

Updated: 2026-06-30

This matrix tracks Electron-like API coverage that is backed by macOS code and regression tests. It is intentionally scoped to APIs that are either implemented or are the next practical compatibility targets.

## Windows / macOS API alignment summary

All public browser-process modules currently exposed by the Windows Electron surface in this tree are now wired on macOS through real native or JS-backed implementations, linked-binding registration, and smoke coverage. No exposed macOS module is backed by empty inert API shells.

| Area | Windows status | macOS status | Remaining delta |
| --- | --- | --- | --- |
| Node/Electron bootstrap | Node environment plus linked native Electron bindings | Aligned: macOS uses real `MacNodeBinding.cpp` / `MacNodeSupport.cpp`, `process._linkedBinding(...)`, and matching Node build macros | None for bootstrap; keep Node macro definitions aligned with `libnodejs.a` |
| Browser exports | app, BrowserWindow, BrowserView, webContents, session, webRequest, protocol, Menu/MenuItem, dialog, Tray, globalShortcut, nativeTheme, powerMonitor, powerSaveBlocker, safeStorage, commandLine, screen, shell, clipboard, nativeImage, systemPreferences, contentTracing, crashReporter, TouchBar, utilityProcess, webFrameMain | Aligned for public module availability and current implemented behavior | Some upstream Electron sub-capabilities remain intentionally absent; see remaining gap table |
| Renderer exports | ipcRenderer, contextBridge, webFrame, remote, screen, clipboard, shell, nativeImage, callbacks registry, isPromise | Aligned for the current public renderer surface | Real renderer-window E2E coverage still needs a deterministic mac renderer harness |
| Common/native helpers | ASAR, v8_util, original-fs, intl-collator, features, MessagePort serialization helpers | Aligned and linked in macOS Electron mode | Add only feature-specific backing when new helpers are needed |
| Public implementation policy | Windows has legacy compatibility shims but public APIs do real work | Aligned: public macOS exports avoid empty inert implementations; unbacked methods are not exported | Add native backing before exposing new methods |

## Remaining capability gaps after 2026-06-30 batch

No public browser-process module from this batch remains absent. The items below are intentionally scoped sub-capabilities where macOS still does not claim full upstream Electron parity because there is no verified native backing yet.

| Module / API | Current state | Remaining delta | Required next step |
| --- | --- | --- | --- |
| `contentTracing` Chromium/Perfetto backend | Public module writes local Chrome trace JSON, exposes recording lifecycle, merges Node/V8 `trace_events` output, and records native lightweight legacy `TraceLog` events | It does not collect Chromium/Perfetto internal service events because the mac Chromium build uses a lightweight trace-event backend | Replace the lightweight trace backend with the full Chromium/Perfetto backend and prove browser/internal events are emitted |
| `crashReporter` native minidumps | Public module writes local crash report JSON, writes Node diagnostic reports, and optionally attempts HTTP/HTTPS upload | It does not capture native minidumps because Crashpad/Breakpad is not present as a linked backend in this tree | Add and link a real Crashpad/Breakpad backend before claiming minidump parity |
